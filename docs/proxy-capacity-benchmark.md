# 单节点容量、技术选型与 Benchmark

## 目标与计量口径

单个 Linux 网关节点的目标区间为 **5–15 Gbps、10–50 万并发 Proxy Session**。先验证 **5 Gbps + 10 万**，再挑战 **15 Gbps + 50 万**。每一档的吞吐与连接数须在同一轮同时达到，延迟、错误率和资源余量须满足事先约定的预算。当前没有实测数据。

- **吞吐。** 统计成功转发的上行和下行代理负载，`goodput = 8 × (Δbytes_up + Δbytes_down) / Δt`。单独报告上下行比例与网卡 RX/TX，避免把同一字节的入站和出站重复计入。
- **连接。** 一条已建立的 Proxy Session 包含一条客户端 TCP 连接和一条上游 TCP 连接。分别记录已建立会话数、实际有流量的会话数、待握手连接数和新建成功会话数每秒（CPS）。
- **延迟。** 分别统计 TCP 已建连到 SOCKS5 认证响应、发出 CONNECT 到收到响应，以及连接内固定负载往返延迟的 P50/P95/P99。使用直连或绕过网关的对照路径评估额外延迟，单列超时和失败。

## 容量分级与技术选择

| 规模 | 候选方案 | 验证后才推进的条件 |
| --- | --- | --- |
| ≤ 5 Gbps、≤ 10 万会话 | Go + Linux，`io.Copy` 起步，保留可计量、可限速的缓冲转发路径 | 跑通多租户、限流、上报与计费，用生产等价路径建立基线。 |
| 5–15 Gbps、10–50 万会话 | 继续用 Go，对比标准库快速路径、缓冲转发和必要时的显式 `splice` | 若剖析确认拷贝是主要瓶颈，先查标准库快速路径为何未命中，再比较显式实现。只有业务能力相同且有稳定收益时才引入 cgo 或其他实现。 |
| 15–40 Gbps、50 万以上会话 | 先比较多节点 Go 与单节点 Rust/Tokio 原型的成本 | 仅在单机密度确有价值，且调优后确认 Go 的运行时开销或 GC 仍使资源或 P99 超预算时，做等价原型。 |
| 40 Gbps 以上、百万级会话或更严 P99 | 独立评估 `io_uring`、Rust 数据面与多节点方案 | 先验证网卡、NUMA、内核和上游可承载目标。对比批量提交、唤醒开销和轮询线程成本，再决定是否引入。 |

Green Tea GC 在 Go 1.25 为实验特性，Go 1.26 默认启用。它能否改善本项目的 P99，需要关联 GC、调度、连接负载和延迟采样验证。 [Go 1.26 发布说明](https://go.dev/doc/go1.26)

Linux 上 `io.Copy` 会优先尝试 `WriterTo` 或 `ReaderFrom`，合适的 TCP 对象可以走标准库的 `splice` 路径。计量包装、握手残留缓冲、限速或加密可能改变实际路径，需在生产等价场景测量。整次 `io.Copy` 的返回字节数通常在复制结束时才可用，周期计量和严格限速需要可观测的分段传输或缓冲路径。 [Go io.Copy](https://go.dev/src/io/io.go) · [Go Linux splice](https://go.dev/src/net/splice_linux.go)

`io_uring` 可批量提交 I/O，某些轮询配置能减少提交系统调用，仍需计入轮询线程、唤醒和内核成本。各档是实验规模，CPU 降幅、吞吐收益和线速都由本项目的 A/B 压测决定。 [Linux io_uring_setup](https://man7.org/linux/man-pages/man2/io_uring_setup.2.html)

## 单机容量预算

| 项目 | 5 Gbps / 10 万会话 | 15 Gbps / 50 万会话 | 假设及验证方式 |
| --- | ---: | ---: | --- |
| 有效负载速率 | 625 MB/s | 1,875 MB/s | 十进制单位。若两侧走同一张全双工网卡，RX、TX 各自都承载约该负载速率，另加协议开销与余量。15 Gbps 档可用 25 GbE 起测。 |
| TCP socket FD 下限 | 20 万 | 100 万 | 每会话 2 个 socket FD。另计监听、握手、队列、`splice` pipe 等 FD，并检查进程及系统限额。 |
| 会话相关内存示例 | 约 6.1 GiB | 约 30.5 GiB | 假设每会话平均 64 KiB，包含两侧 socket、用户态缓冲、栈和会话状态。分别按 16–128 KiB 做敏感性分析，约为 1.5–12.2 GiB 和 7.6–61.0 GiB，再加进程基线与峰值余量。 |
| 同一上游地址的出站源地址量级 | 至少 4 个 | 至少 18 个 | 示例按每个源 IP 至同一上游 IP:port 可用 28,232 个端口（32768–60999）计算，未计端口保留、TIME_WAIT 或 NAT。多出口、多源地址或多节点需一起规划，压测机也要检查端口。 |
| 稳态建连速率示例 | 约 333 CPS | 约 1,667 CPS | 平均会话 300 秒，`CPS ≈ 并发会话数 / 平均时长`。短连接和重连风暴另测。 |
| 用量事件速率示例 | 约 1 万条/s | 约 5 万条/s | 每 10 秒一个事件且所有会话都持续产出，另计关闭补报和重投。按实测活跃比例、批量策略及同步刷量峰值校准。 |

临时端口范围以部署环境读数为准。RSS、软中断和 NIC 队列按核检查，避免被整机 CPU 平均值掩盖。 [Linux IP sysctl](https://docs.kernel.org/networking/ip-sysctl.html) · [Linux 网络栈扩展](https://docs.kernel.org/networking/scaling.html)

## 压测矩阵

| 测试 | 做法 | 要回答的问题 |
| --- | --- | --- |
| 基础转发 | 独立压测机和可控 SOCKS5 上游。先大流、小流、上下行偏斜，再比较缓冲转发与标准库快速路径。 | NIC、CPU、内核或拷贝谁先饱和？ |
| 会话密度与建连 | 分开测试空闲、低流量会话及高频建连，逐级增加到 10 万、30 万、50 万。分别测鉴权缓存热、冷和击穿场景。 | 内存、FD、端口、握手和控制面分别在哪里触顶？ |
| 混合负载 | 在两档目标上同时启用鉴权、限流、计量、真实队列及消费。用代表性租户分布跑长连接和突发流量，再单独验证真实第三方上游。 | 同时达标时的 P99、计费正确性和资源余量是多少？ |
| 故障与扩缩容 | 注入上游超时、Control 不可用、队列积压与重投。模拟网关异常退出、实例扩容和下线排空。 | 新连接能否恢复，存量连接受多大影响，用量是否丢失或重复扣费？ |

每组建议先预热 5 分钟、稳态 30 分钟并重复 3 次，另做 2 小时混合负载观察内存与积压趋势。这是起测参数，可按负载周期调整。记录 Go 版本、内核、CPU/NUMA、NIC、网络拓扑、限速模式、数据包大小和流量模型。A/B 保持这些变量及业务功能一致，使用客户端与目标端字节计数交叉核对。

## 每轮必须记录的指标

| 类别 | 指标与排查方向 |
| --- | --- |
| **核心** | 单节点 goodput、活跃会话数和有流量会话占比、CPU 总量及最忙核、各阶段 P99、握手/CONNECT 失败率和超时率。记录达标点与首次饱和点。 |
| 资源与内核 | 用户态、内核态和软中断 CPU，CPU 核数/Gbps，RSS、Go heap/GC CPU 与暂停、调度延迟、socket 内存、FD、临时端口失败、重传和 NIC 丢包。 |
| 控制面与账务 | 鉴权缓存命中率、鉴权 QPS/P99、CPS、消息发布失败与积压年龄、事件至扣款可见时延、重投去重、网关转发字节与账单字节差异。 |
| 弹性与恢复 | 新实例达到可接流时间、摘流后误入的新连接、存量连接被强制关闭数、排空时长、末批事件未入账数量。 |

启动前约定各阶段 P99、错误率、CPU 余量和用量丢失预算。重复事件在验收中须做到零重复扣费。若首次超预算来自上游、端口、网卡或队列，先修对应瓶颈。确认是转发拷贝或运行时开销后，再进行 Go 快速路径、显式 `splice` 或 Rust 原型对比。

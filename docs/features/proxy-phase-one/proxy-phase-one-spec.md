# Proxy 一期 Spec｜隧道用量闭环

[GitHub Issue #1](https://github.com/DuanJinTaoToday/proxy/issues/1)

**状态：已确认一期口径。** 原版 GOST 文件 Recorder 是计量来源。网关侧采集器每秒通过 HTTP 批量上报给 `proxy-control`，以本地文件作为待确认记录的重放来源。成功建立的代理会话可计入 SOCKS5 协议字节，失败连接不计用量。已完整写入文件的记录在 GOST 进程重启后须可补报。跨午夜的增量归到后一个采样所在日。

## 交付目标

企业租户使用平台凭据，经 `proxy-gateway` 和悟空访问目标。租户在控制台查询自己的每日上下行流量，运营用同一口径按租户查询，并能追到构成汇总的原始记录和可能的用量缺口。API 提取和悟空流量查询先做 Mock，静态 IP 与计费规则保持在已约定的建模范围。产品边界及悟空联调前置条件见[一期对齐文档](../../product/proxy-product-alignment.md)。

## 用户故事

1. 作为租户成员，我使用平台发放的凭据连接 SOCKS5 网关，能通过悟空访问目标。无效凭据无法接入。
2. 作为租户成员，我选择日期范围，只能看到本租户的每日上行、下行、合计和最近入库时间。长连接在关闭前也能更新用量。
3. 作为运营，我可按租户和日期查到与租户侧一致的用量，并从汇总追到网关实例、启动代次、客户端标识、代理会话、原始采样和纳入汇总的差值。
4. 作为运营，我能区分上报积压与异常退出后的可能缺口。记录已写入网关文件时，可以恢复采集。未写入的数据量未知，页面和告警不估算丢失字节。
5. 作为开发人员，我可以用两个 Mock 租户验证统一提取、`IP_List` 返回及流量查询归属。模拟用量与真实隧道用量隔离，等待悟空部署后再验证真实直连及用量查询。

## 网关计量与采集

- `proxy-gateway` 运行原版 GOST `v3.3.3`，使用 SOCKS5 TCP CONNECT 和悟空上游连接配置。认证插件由平台校验代理凭据并返回稳定的 `clientID`，采集时使用平台可信映射解析租户，避免历史记录因凭据迁移被归到新租户。Observer 用于监控。
- 用量采用合格会话的 Recorder `inputBytes`、`outputBytes` 累计值，分别对应客户端侧的上行、下行。该口径允许计入成功会话的协议字节，因此成功但无业务数据的会话仍可能有非零用量。对固定版本，先要求 `network=tcp`、`clientID`、`src`、`dst` 都满足已建立会话条件，并检查 `err`。策略拒绝可能没有 `err`。合格会话规则要用成功、空连接、上游拒绝、超时和网关策略拒绝的样本锁定。
- 网关侧部署独立采集器，与 GOST 共享本机 Recorder 目录。GOST 写入 `interim` 和 `final`，采集器每秒检查待发的完整记录，有数据时经带服务身份认证的 HTTP 接口批量上报，每批限制记录数和字节数。`proxy-control` 可独立部署在另一台机器。上报周期与 GOST 自身的采样周期分别配置。每个 GOST 启动代次使用可识别的文件，轮转文件保留稳定标识。重启后采集器继续读取旧文件并开始采集新文件。
- 每条记录携带网关实例、启动代次、文件标识、记录起始偏移和 Recorder 内容。用四个来源字段组成稳定的记录 ID，重放时 ID 不变。对同一网关启动代次，采集器按源文件顺序组批，上一批确认后再发送下一批，控制面按批内顺序处理，避免后采样先入库导致跨日归属错误。
- 采集器收到 `proxy-control` 的**整批入库确认**后，才推进本地持久化偏移，且只推进到连续已确认的位置。HTTP 超时、可重试错误、服务停机或确认丢失时保留源文件，从未确认位置退避重试，恢复后继续按序发送。请求被永久拒绝时保留原文件并告警。轮转文件只在文件关闭且所有记录均已确认后进入清理流程。监控文件写入失败、待上报字节与最老未确认记录时间，以及磁盘水位。
- 运营明细保留计量和追溯所需的原始字段，保留 `recordIndex`、`phase`、累计值、记录时间、采集来源和接收时间。禁止记录凭据或业务报文到用量库。Recorder 源文件包含连接元数据，限制文件访问，并在实现前明确保留期限。

## 控制面归集与故障边界

- `proxy-control` 对每批在一个数据库事务内按记录 ID 去重，以 `(gateway_id, boot_id, sessionID)` 锁定检查点，保存原始记录、认可的用量差值和终态。**整批提交成功后才返回 HTTP 成功确认**。已入库的同一记录重发不增加用量。同一 ID 内容不同、无法解释的累计倒退及租户身份冲突需留证告警，不覆盖检查点。能识别来源但无法归集的记录须随批持久化隔离后才可确认。事务失败时整批不确认，由采集器重发。
- 检查点从零开始，相同累计增加 `0/0`，累计增长只计差值。已确认的旧记录重放不得让累计倒退或让已闭合会话重新打开。`recordIndex` 只用于追溯，因为相同索引可以带更新的累计值。累计相同的 `final` 仍可关闭会话。
- 租户与运营复用同一聚合。将认可的增量按本次 Recorder 记录时间归入 `Asia/Shanghai` 自然日，补报回到原记录日期。两次采样跨午夜时，增量统一归到后一个采样所在日。生产采样周期与验收时效在联调配置中明确。
- 生命周期事件或心跳由 GOST 进程外的组件采集，无流量时也能发现异常退出。文件采集器在旧代次已写记录全部获得入库确认后，发送带旧代次标识的回放完成通知。控制面再核对仍缺 `final` 的会话并保留可能缺口。提示区间从最后一份已持久化采样时间至发现退出，缺失字节量未知。没有已知会话记录时仍可提示网关代次级缺口。
- 持久化承诺以明确的故障场景验收。当前只证实写入本地文件的数据跨 GOST 进程重启仍可读取。宿主机掉电、磁盘故障和采集器持久化位置尚待验证。HTTP Recorder 直投只作为验证参考，实测 `final` 返回 503 后未见重发，不能承担需要回放的主链路。

## 验收与测试入口

主测试入口是 GOST 写文件、采集器批量 HTTP 上报、`proxy-control` 查询用量的完整链路。先用受控 SOCKS5 上游提供可复核的会话和字节样本，在 HTTP 确认与进程边界注入故障。最后用真实悟空入口验证跨机器部署及两个租户的权限和查询结果。

| 验收项 | 操作与预期 |
| --- | --- |
| SOCKS5 转发与用量准入 | 受控上游覆盖成功、成功空连接、拒绝、超时及网关策略拒绝。符合已建立规则的会话按原生累计计量，其余记录可排查但汇总增量为零。以真实悟空入口和两个租户做端到端冒烟。 |
| 文件回放与幂等 | 首段累计 `130/214` 已提交。后段 `180/294` 已写文件但未采集，强杀 GOST 后恢复采集，仅增加 `50/80`。复拉同一累计增加 `0/0`。另测采集器重启、文件轮转、相同 `recordIndex` 累计增长及零增量 `final`。 |
| 跨机器与批量确认 | 网关侧采集器和控制面分开部署，控制面无 Recorder 目录挂载。健康时每秒有数据才发，批次不超过上限。控制面停机或事务失败时偏移不推进，未确认文件可恢复。数据库提交后丢失 HTTP 响应，或采集器在确认后写偏移前重启，重发只计一次。 |
| 进程异常退出 | 尾段未写文件即强杀 GOST，已入库数据保留。旧文件回放后仍缺 `final` 的会话显示可能缺口。新进程使用独立代次，即使没有流量也能检测退出。 |
| 单实例容量与集中关闭 | 在目标部署环境运行原版 GOST v3.3.3 和文件 Recorder。按候选连接上限建连后触发集中关闭，同时以预先约定的速率持续发起新 SOCKS5 连接。新连接成功率、成功样本端到端 P99 和 Recorder 记录完整性均通过后，才将该负载计入单实例上限。 |
| 租户与运营 | 两个租户无法互查。授权运营对同一日期范围查到同样的汇总，可从原始记录和认可增量复核。用 `23:59` 的 `130/214` 和次日 `00:01` 的 `180/294` 验证 `50/80` 归次日，晚到回放结果相同。 |
| 提取 Mock | 测试两个供应商标识映射到正确租户、重复拉取不重复计量、未知标识隔离、仅总流量时不伪造上下行。真实提取等待悟空部署。 |

补测在 GOST `v3.3.3` / `go-gost/x v0.28.1` 和本地受控 SOCKS5 环境完成。HTTP `interim` 上报失败后，在会话和进程仍存活时可由后续累计覆盖。`final` 失败后未见重发。文件 Recorder 的后段已写文件但未采集时，GOST 重启后可回放 `50/80`。这两组实测支持文件采集方向。 [Recorder 结束会话源码](https://github.com/go-gost/x/blob/v0.28.1/recorder/session.go#L55-L86)

### 集中关闭压测口径

压测前固定候选连接数、新连接发起速率、以集中关闭触发时刻为起点的观测窗口、单次探测超时，以及三项通过阈值。探测从开始连接到收到 SOCKS5 CONNECT 成功响应计时，包含 TCP 建连、认证和上游连接。按观测窗口内发起的探测归组，等每条探测成功、失败或超时后再统计。

1. **新连接成功率。** 成功数除以窗口内发起总数，失败和超时都计入分母，并分别报告成功、失败与超时数。
2. **新连接端到端 P99。** 仅用成功探测计算 P99，同时报告失败与超时数，避免成功样本的延迟掩盖连接失败。
3. **Recorder 记录完整性。** 将本轮已完成且符合计量口径的测试会话逐条与 Recorder 文件核对。预期会话的 `final` 齐全且各出现一次，允许同一会话有多条不同的 `interim`。检查缺项、重复及坏行，记录从触发关闭到全部预期记录可读的时间，并与约定时限比较。

单实例上限以目标环境中三项都通过的最高已验证负载为准。当前不承诺 10 万并发。目标阈值待确定，持续高频短连接和真实悟空链路仍需验收。

本机对照仅用作压测基线。Windows 上单个 GOST 进程的 8 个回环入口共用同一个文件 Recorder，使用本地 Unix socket 模拟上游。两轮交换开关顺序，开关组参数一致，各组成功建立并集中关闭 100,000 条连接。下表统计触发关闭后 3 秒内发起的探测，P99 仅含成功样本。

| 轮次 | Recorder | 新连接失败数 / 发起数 | 成功样本 P99 | 文件读齐耗时 |
| --- | --- | --- | --- | --- |
| 第一轮 | 关 | 0 / 594 | 2.593 秒 | — |
| 第一轮 | 开 | 116 / 574（20.2%） | 2.988 秒 | 3.637 秒 |
| 交换顺序复测 | 关 | 0 / 591 | 2.928 秒 | — |
| 交换顺序复测 | 开 | 52 / 587（8.9%） | 2.974 秒 | 3.318 秒 |

开启 Recorder 的两轮均按预置客户端地址和会话 ID 核对了 100,000/100,000 条记录，未见缺项、重复或坏行。读齐仅表示本地文件可读，宿主机掉电耐久尚未验收。关闭 Recorder 时集中关闭也推高了新连接延迟，开启时两轮均出现新连接失败。

## 部署参数与范围

首个切片从单网关和一个批量 HTTP 接口开始。正式上线前明确 GOST 采样周期、批次大小、请求超时、退避策略、文件保留期限、控制面离线窗口及磁盘水位处置策略。离线期间由网关磁盘承接未确认记录。本期承诺针对 GOST 进程重启和采集重放，宿主机掉电、磁盘丢失或超过保留窗口的恢复能力另行验收。

定价、扣款、出账和结算安排在后续阶段。静态 IP 先做领域建模。真实 API 提取及流量查询在悟空部署并提供可按租户查询的接口后联调。

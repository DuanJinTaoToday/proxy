# GOST 租户流量原型

这个原型验证原版 GOST 能否承担 SOCKS5 网关和满足一期计量。运行官方 GOST v3.3.3 Windows amd64 二进制，依赖 go-gost/x v0.28.1。本地实验由两个租户身份、一个带认证的受控 SOCKS5 上游、一个有确定字节量的 TCP 目标，以及 HTTP 认证和 Observer 接收器组成。全部绑定回环地址。SQLite 只用于验证原始记录、累计检查点和重启提示持久化。代码和配置用于复现实验。

## 复跑

从 [GOST v3.3.3](https://github.com/go-gost/gost/releases/tag/v3.3.3) 获取对应平台二进制。此次 Windows amd64 ZIP 的 SHA-256 为 `b00441624a66ebed94a2ddcc01ab2832069f053e6ca0abf19d7104b84fad1f78`，与 GitHub 发布资源摘要核对一致。使用本目录的 `run.py`，输出目录应当不存在。

```powershell
python -B .\run.py C:\path\to\gost.exe --out .\gost-lab-output
```

运行后保留临时 SQLite、配置、GOST 日志、原始 Observer 请求和结果 JSON。仓库只保留 [本次结果](report.json)和[原始上报样本](observer-attempts.json)。所有账户都是实验值。

## 实测结果

| 场景 | 预期业务字节（上行 / 下行） | 原生 Observer 或接收结果 |
| --- | --- | --- |
| 租户 A | 1,024 / 2,048 | `tenant-a` 1,024 / 2,058 |
| 租户 B | 512 / 256 | `tenant-b` 512 / 266 |
| 建连后零业务数据 | 0 / 0 | 0 / 10 |
| 上游拒绝 CONNECT | 0 / 0 | 0 / 10 |
| SQLite 已提交，确认丢失 | 111 / 222 | GOST 重传相同事件，适配器只加 111 / 232，重传的增量为 0 / 0 |
| 接收端连续两次返回 503，随后恢复 | 444 / 777 | 拒绝期间未入库，恢复后增加 444 / 787 |
| 接收端拒绝期间强制结束 GOST，再启动同名服务 | 321 / 654 | 旧进程未确认的一段未补报，已入库总数保持。新进程的 123 / 234 另计为原生 123 / 244 |

未授权身份在连接上游前被拒绝。两个有效身份由认证插件映射为各自租户 ID。原始 Observer 事件含服务名、客户端 ID 和累计流量。接收端附加网关实例、启动代次和接收时间，并把原始统计、检查点和归集增量保存在一个事务中。上报确认丢失的场景验证了单实例、单代次有序上报下的去重。

重启后，接收器记录旧代次最后一次成功接收时间和新代次首次接收时间，标记**可能缺口**。只有实验知道缺失了多少业务字节，因为受控目标提供了真值。生产接收端单靠原生 Observer 无法算出缺失量。原型以新代次首次上报触发提示，重启后没有流量时仍需独立的实例生命周期信号或心跳。

## 对 Spec 的建议

- 复用 GOST 的 SOCKS5 入站、认证插件和上游转发配置，保留平台发放凭据与租户映射。实际悟空入口冒烟尚未运行，本机未注入接入记录所需的 `SEEDPIPE_PROXY_PASSWORD`。
- **一期约定的业务字节需要计量扩展。** 原生 Observer 计的是客户端侧读取和写入，样本中的下行多出 10 字节 CONNECT 响应，上游失败也出现了下行流量。不能按连接数固定减 10 来作为计量方案，响应编码可能不同，上行读到的数据也可能未成功写往上游。优先在 GOST 的实际双向转发写入处加小范围扩展，按写入返回的有效字节累计，排除 SOCKS5 协议响应。当前原型只测了原生行为，扩展尚未实现。
- 接收端可复用原生插件协议的租户和服务字段。正式上报仍需明确稳定的网关实例、启动代次、采样时间或计量窗口、重传标识与原始记录查询。原生请求样本没有这些时间及代次字段。原型的时间区间只是接收时刻之间的可能缺口，用它不能还原跨日用量归属。
- 明确持久化边界。已提交的数据可按已验证的检查点模式去重，进程内未确认的数据在崩溃时可能消失。应为运营暴露可能缺口，同时把真实网络、跨日归属、持久化前丢失范围和上线性能纳入后续验收。
